The Micro OS wiki¶

Micro OS is a Linux-like kernel for small machines: one portable core, and a port per kind of machine. This wiki is the user guide - how to build the system, drive its shell, find a file, run a program, and fix what does not work.

The canonical documents stay in docs/: the architecture, the roadmap, the ABI and the decisions of the project. This wiki links to them rather than copying them, and when a page here and a document there disagree, the document is right. There is no Russian translation of the wiki yet; the canonical Russian documents are in docs/ru/.

Serving the wiki as a site¶

mkdocs.yml in the root of the repository is a draft of a site: it is not a part of the build and make ci does not need it. The pages are plain Markdown and GitHub renders them as they are. To serve them locally:

python3 -m pip install --user mkdocs mkdocs-material
mkdocs serve                  # http://127.0.0.1:8000
mkdocs build                  # writes site/, which is generated

docs_dir is docs/wiki, and MkDocs reads this file as the home page of the site. The theme is material; if mkdocs-material is not installed, replace theme: material with theme: readthedocs in mkdocs.yml and plain mkdocs serves the pages. The wiki links into the rest of docs/ on purpose, so a build may warn about targets that live outside the site; the links themselves are checked against the repository by the script below.

Checking the links¶

python3 tools/wiki_check.py                  # docs/wiki, every link and anchor
python3 tools/wiki_check.py docs/wiki/shell.md  # one page
python3 tools/wiki_check.py --verbose        # one line per page

The script fails on a target that does not exist and on an anchor that no heading of the target file produces. It is run by hand today; the natural place for it is make integrity (or a step of make ci next to the other repository checks), which is a change of the Makefile and not a part of this wiki.

What the wiki does not do¶

The wiki does not replace the design documents, the ADRs or the phase reports: it explains how to use the system, not why it is shaped the way it is. It also does not promise what the tree does not do - a feature that is planned is marked as planned, and the roadmap is the place where its status is kept.
