Programs¶

A program in Micro OS is a file, not a function of the kernel: execve reads the file through the VFS, the kernel checks it against a format of its own, and the port places it in memory and enters it. The decisions are in ADR 0005 (the format and the rights), ADR 0006 (the entry), ADR 0007 (the address space and ring 3) and ADR 0016 (the environment, the library and the programs of /bin); the report of the phase is docs/phases/phase7.md.

Two machines of the tree can run a program today:

Machine k_port_exec_supported() k_port_exec_arch() What execve answers
x86-64 in QEMU true 0 (x86-64) it runs the image in ring 3
ESP32 board true 1 (Xtensa) it runs the image in the kernel's address space (no protection)
host simulator false 0 on x86-64, -1 elsewhere ENOSYS for its own machine, ENOEXEC for another, ENOSYS on a host of a machine the format does not know
null port false -1 ENOSYS

A port that cannot enter a program still names the machine it is, because the machine is a fact about the processor and the loader is a separate promise. The arch of the header is compared with k_port_exec_arch() before the port is asked anything: an image of another machine is ENOEXEC, and no byte of it is entered - the board checks this against a hand-made x86-64 image at every boot. In the simulator the shell still has exec; it looks for the file, checks the execute bit, and then reports why the program did not run. That is the contract working, not a missing build.

The format: MOX1, version 2¶

An executable is a flat image: a header of 32 bytes, then the code, then the initialised data. The bss is not in the file; the port clears it. The layout is in components/kernel/include/kernel/exec.h:

Offset Field Meaning
0 magic the bytes M, O, X, 1
4 version 2
8 flags 0; a flag the kernel does not know is a refusal
12 entry the offset of the first instruction, from the start of the image
16 text_size the bytes of code
20 data_size the bytes of initialised data
24 bss_size the bytes to clear, at most 1 MiB
28 arch the machine of the bytes: 0 x86-64, 1 Xtensa
32 the text, then the data

Version 2 is version 1 with the machine in the last field, which version 1 kept reserved and zero. The bytes of one machine are not the bytes of another, so an image says which machine it is for, and a reader that does not know a version refuses it instead of guessing at the meaning of the bytes. This kernel reads version 2 and refuses version 1 (and a later generation) with a sentence in the kernel log that names the version it reads; the call answers EINVAL.

The parser (components/kernel/src/exec.c) checks the image against itself and nothing else: the magic and the version, an arch that is one of the two machines of the format, the sizes against the file, a text that is not empty, an entry inside the text, sizes that are multiples of four, a known flag, and a bss under a megabyte. Whether the image fits the window of the machine, and whether it is the right machine at all, is between the caller of k_exec_run and the port, asked later.

tools/mkprog.sh turns a linked object into an image:

tools/mkprog.sh [--base 0x02000000] [--data-base 0x3FFCE000] \
                [--arch x86-64|xtensa] hello.elf hello.mox hello_main

The image is not relocated: the code and the data have to be linked for the address the port names, and --base makes the script refuse an image linked for another window. --arch writes the machine into offset 28 and defaults to x86-64; a name the format does not know is refused before an image is written. --data-base is for a port whose data is a window of its own (the board): the data no longer follows the text, so the script checks its address against that number instead of the contiguous rule and also checks where the bss will be cleared. The x86-64 port builds its thirty-one images this way: the object is compiled for the window, linked with programs/program.ld, turned into a .mox by the script (--base 0x02000000 --arch x86-64), and written into the MicroFS volume of the disk by make x86-disk (see below). The kernel carries no copy of a program. The board builds hello and cat with --arch xtensa --base 0x4009E000 --data-base 0x3FFCE000 and the toolchain of ESP-IDF (ADR 0018).

The programs on the disk¶

A program is a file of a volume, and the volume is a property of the disk of the machine. The image of the x86-64 port is made by a host tool that links the filesystem of the board, so the format of the volume has one implementation:

make x86-disk      # build-x86/programs.img: MBR, one partition, MicroFS
make x86-run       # boot that image; /bin/hello runs before the shell
make x86-smoke     # the same, driven by the smoke test

tools/mkfs_mfs.c writes the image: an MBR with one Linux partition at LBA 2048, a MicroFS volume in it, /bin, /etc and an empty /etc/init.d, the thirty-one .mox images of the build written to /bin with mode 0755, the licenses of zlib, PCRE2, Lua, zstd, sbase, bc, file and SQLite in /etc/licenses, the scripts /etc/hello.lua, /etc/hex.lua, /etc/bc.bc, /etc/dc.dc and the fixtures of the database (/etc/sql-*.sql), the fixtures of the two compressions (/etc/greeting.gz, /etc/setting.zst, /etc/broken.zst), the database of libmagic (/etc/magic.mgc and its text), and the settings of the machine in /etc/setting. It does not repeat the layout of MicroFS: it is a block device over a range of the file, and components/mfs formats it and writes the objects through mfs_create, mfs_write and mfs_chmod. The host test tests/cases/test_mkfs_image.c reads the bytes back with the same mfs_* calls, mounts the volume and checks /bin/hello, /etc/init.d and /etc/setting.

The boot also mounts /proc and /dev (the same procfs and devfs the board and the simulator mount), so the root of x86-64 is the root of every port: tree / draws bin/, etc/ (with init.d/ and setting), proc/ and dev/. /etc/setting is data of the image:

hello
hostname=x86_64
console=vga

A volume without /etc (the memory volume of a machine with no disk) gets the directory and the file from the boot; a volume that already has them is never changed.

/bin and the boot¶

The x86-64 port mounts the MicroFS volume of its disk at / and finds /bin already there: the thirty-five images are files the tool wrote, with the mode of a program (0755), and no boot creates one:

File What it proves
/bin/hello the door: write, arguments, environment, pid, clock, sleep, exit; it prints cpl 3
/bin/crash a fault of ring 3 is reported and the shell survives
/bin/fork fork() with copy on write: the child gets 0, the parent the pid
/bin/procs the POSIX pair of a program: a child computes and returns its status, a double fork, and an execve that replaces the child that called it
/bin/fpu2 the floating point state of a task: three tasks compute in double at once and keep their own XMM and x87 registers, and an execve starts the new image after fninit
/bin/badptr a pointer outside the window is EFAULT, not a fault of ring 0
/bin/signals a handler, SIGTERM ending a child, a wait cut by SIGINT, SIG_IGN, and the errors of kill
/bin/nx the protection of the pages: a fetch of its data, a write to its text and a call that hands its text to the kernel, each taken down, and a parent still alive
/bin/cat sbase: open, read, write on a file or descriptor 0
/bin/echo the vector of the arguments and write, the shortest useful program
/bin/ls sbase: a directory through open(O_DIRECTORY) and readdir, -l, -a, -R and --color; no path is the working directory
/bin/pcre2grep the lines of a source that match a regular expression (-i, -v, -n, -o, -g N), through the vendored PCRE2
/bin/grep sbase: a regular expression over the lines of a file (-i, -v, -r)
/bin/head sbase: the first lines of a source (-n N)
/bin/tail sbase: the last lines of a source (-n N)
/bin/wc sbase: the lines, words and bytes of a source (-l, -w, -c) or of descriptor 0
/bin/sort sbase: the order of the lines (with -n)
/bin/find sbase: a walk of a tree with -name
/bin/xargs sbase: a command over the words of a pipe; every command is a child of its own and -P N keeps N of them running
/bin/sed sbase: a substitution, line by line
/bin/mkdir a directory through mkdir, one for every word of the line
/bin/pwd the directory of the task through getcwd
/bin/rm a name through unlink; -r walks a directory with readdir
/bin/spawn execve from a program, with an environment of its own; the image replaces the caller
/bin/zcat a .gz of the VFS inflated by zlib 1.3.1 and written to the console or a file
/bin/lua the interpreter of Lua 5.4.7: -e, the script /etc/hello.lua, io and os.time
/bin/pcre2grep a regular expression of PCRE2 over a file or a stream
/bin/bc the calculator of bc 7.2.0: -e, -f, a script, -l and scale, ibase/obase
/bin/dc the same engine in RPN: a stack, the operators and the printing command p
/bin/zstd the command of zstd 1.5.7: -d, -c, -f, -q, -l, -t, -1..-19, --rm, -o, a pipe, and the frames of every other zstd
/bin/zstdcat the same image under a second name: it unpacks to standard output
/bin/file the type of a file through libmagic of file 5.45 (-b, -i, -z for a gzip and a zstd frame, -f for a list) and the compact database /etc/magic.mgc
/bin/sqlite3 the shell of SQLite 3.54.1 (public domain) over a database file of MicroFS: .read, .tables, .schema, .mode, .timer, -cmd and -batch
/bin/awk the One True Awk of 2024-07-28: the fields, -F, -v, -f, printf with a width and a precision, getline, the arrays, the functions of math.h, and a refusal of system and of a pipe (no shell)
/bin/ui the skeleton of ADR 0028: /dev/fb0 and /dev/input0, a panel, a list of windows and the log; Tab moves the focus and q gives the screen back
/bin/edit a text editor (ADR 0030): a file, the arrows and the characters of /dev/input0, Ctrl+S, Ctrl+Q, a title bar and a status line; a modal window asks about an unsaved file
/bin/fm a file manager (ADR 0030): the directory through readdir, Enter to open a directory or /bin/edit, d/Delete with a modal question and unlink, q

The first six talk to the kernel through programs/prog.h, because what they test is the raw door, the fault, the fork, the edge and the signals. echo, mkdir, pwd, rm and spawn are ordinary C programs linked against components/libc/user (ADR 0016); zcat, lua, pcre2grep, zstd, bc/dc, sqlite3 and awk are linked against the seven libraries of somebody else (zlib, Lua, PCRE2, zstd, bc, SQLite and the One True Awk), file is linked against libmagic of file 5.45, and the ten commands of sbase are the commands of the machine under their canonical names (docs/porting-programs.md, third_party/sbase, third_party/zstd, third_party/file, third_party/sqlite, third_party/awk). Every one of them reads descriptor 0 when it is given no file (or -); execve carries the table of the caller, so a redirect or a pipe of the shell fills it (cat < file, ls /bin | wc -l, ADR 0017). A program at the prompt with no redirect still has no descriptor 0 of the console.

The shell looks a bare name in PATH before its own table for the ten commands: ls /etc at the prompt is /bin/ls, the same file exec /bin/ls /etc runs. The command of the shell is the fallback of a machine without programs (the simulator) or a file that is not there (the board). What the shell keeps for itself is the state and the special commands: cd, path, df, mount, fsck, stat, write, mkdir, rm, tree, kill and config. The small ls, cat, grep, wc and head of ADR 0016 are not built for this port any more, and /bin/ls is the ls of a Unix-like system: -l, -a, -R, --color[=always|never|auto] (a directory in blue and an executable in green; auto is off, because the shell has no terminal to ask).

The volume also carries /etc/greeting.gz, the fixture of zcat: a gzip stream of a fixed text, written by tools/x86_image.py with mtime from SOURCE_DATE_EPOCH and no file name in the header, so two builds of the image write the same bytes. zcat -o FILE inflates it into a file of MicroFS and zcat -t checks it; the smoke tests compare the count and the text of the inflated bytes. /etc/hello.lua is the first script of the machine, read by the interpreter out of the volume; /etc/bc.bc and /etc/dc.dc are the scripts of the calculator. The licenses travel beside the programs that carry the libraries: /etc/licenses/zlib, /etc/licenses/lua, /etc/licenses/pcre2, /etc/licenses/sbase and /etc/licenses/bc; docs/licensing.md has the rows.

The ten commands of sbase are the commands of the machine under their canonical names: /bin/ls is the ls of a Unix-like system (-l, -a, -R, --color), /bin/cat is cat and the same for the other eight. The small ls, cat, grep, wc and head of ADR 0016 are not built for this port any more; /bin/echo, /bin/mkdir, /bin/pwd and /bin/rm stay because sbase does not have them.

The shell looks a bare name in PATH before its own table for these ten (shell.md), so ls /etc is the program of the disk and not the command of the shell. The simulator has no port to enter an image and keeps the commands of the shell; the board has no ls of sbase in /bin and falls back to its own.

/etc/bc.bc is a bc script with a power, a square root, the two bases, a function with a loop, an array, a string and the math library of -l, and /etc/dc.dc is the same engine in RPN. bc -l -f /etc/bc.bc < /dev/null reads the first, bc -l < /etc/bc.bc reads it on descriptor 0, and dc /etc/dc.dc runs the second. The shell does not give a program at the prompt a descriptor 0, so a bc with a file and no redirect ends with a fatal I/O error after the file (docs/debts.md); bc -e does not read stdin and needs no redirect.

The boot then asks for /bin/hello with ksys_execve(): the stat, the check of the mode, the read through the VFS, the parse and the entry are the ones of the call and not a copy of them. The shell runs the same file with exec.

The volume also carries the database of file: /etc/magic.mgc (the subset of the Magdir files compiled by the build, 349 KiB) and /etc/magic (the same text, the fallback when the compiled file is not there). /etc/hello.lua is the fixture of the Lua rule: a script with the shebang the database names, so file /etc/hello.lua is Lua script, ASCII text executable, and /etc/licenses/file is the BSD-2-Clause notice beside the program.

/etc/setting.zst is the fixture of zstd, written by the zstd of the machine that builds the image (tools/x86_image.py): the guest unpacks a frame of the host, and make x86-smoke reads a frame the guest wrote back out of the machine (as hexadecimal, by /etc/hex.lua) and unpacks it with the host, so the two directions of the format are in the tests. /etc/broken.zst is the same frame with its tail cut, which zstd -t refuses. /etc/licenses/zstd is the BSD-3-Clause of the release beside the commands that carry the library.

The other two interpreters have their fixtures the same way: /etc/hello.lua for /bin/lua, and /etc/columns and /etc/hello.awk for /bin/awk (three colon-separated records and the script that counts and sums them). Their licenses are /etc/licenses/lua and /etc/licenses/awk.

The board: Xtensa code without an MMU¶

The board runs a .mox of arch 1 (Xtensa), and the price is written on the first line the program prints: there is no protection. The program is a task of the kernel with the kernel's own address space; a write to its text or a bad pointer that reaches the kernel is a fault of the machine, and the board prints Guru Meditation and reboots (ADR 0018 §4, docs/debts.md).

The loader cannot put a C program in one window. The ESP32 has two kinds of memory and the code needs both:

Window Address Size What lives there
instruction RAM 0x4009E000..0x400A0000 8 KiB the text and its .literal pools
DRAM 0x3FFCE000..0x3FFD0000 8 KiB the data, the bss and the vectors (argc, argv, envp)

The instruction RAM is executable and writable but only 32-bit accessible for data; a byte read of a string there is a LoadStoreError (the Kconfig option that emulates it would turn every character of printf into an exception). The DRAM is byte-addressed and not executable. The two windows are the top of iram0_0_seg and the top of the static DRAM segment; the build fixes the size of the static segment (CONFIG_ESP32_USE_FIXED_STATIC_RAM_SIZE) so the heap starts at 0x3FFD0000, and components/port_esp32/exec_windows.ld refuses a kernel that grows into either window. A program of the board is therefore limited to 8 KiB of text and 8 KiB of data, one at a time: a program that calls execve would overwrite the code it is running from, and the port answers ENOMEM.

The door is a function, not an instruction. The syscall instruction of the Xtensa is taken by the vector of ESP-IDF before the port sees it (ADR 0018 §3a), so the loader passes the address of port_mox_syscall(nr, a0 ... a5) - the shape of ksys_call() - as the first argument of _start, and the library keeps it for every wrapper. The numbers and the results are the ones of kernel/ksys.h, the same as on x86-64; only the crossing differs. The entry is _start(void *door, long argc, char *const argv[], char *const envp[]) in the windowed ABI of the machine.

The programs are files of the progs partition, mounted read-only at /bin (ADR 0022): hello and cat are two .mox files at 64 KiB boundaries, the partition is built by tools/progs_image.py and flashed with the image, and execve reads the bytes through the VFS. There is no image of a program in the firmware. An image of x86-64 is written to /log/.foreign at the boot only to be refused. tools/device-test.sh runs hello at the boot (twice, through execve) and from the shell, lists /bin, and checks that /log/.foreign answers ENOEXEC before a byte of it runs:

microos> exec /bin/hello one two
PROGRAM: hello from /bin
PROGRAM: arch xtensa, no protection
PROGRAM: /bin/hello is 2152 bytes, mode 493
PROGRAM: argc 3
PROGRAM: argv[0] /bin/hello
PROGRAM: argv[1] one
PROGRAM: argv[2] two
PROGRAM: envp 4, PATH=/bin
PROGRAM: pid 10, up 32477 ms
PROGRAM: exit 0
task: 'program' (pid 10) exited with code 0
esp32: the program exited with 0
the program has finished

The mode is printed in decimal (493 is 0755), and the lines of the kernel (task: ..., esp32: ...) are left in the transcript because they are part of the boot console of the board.

/
the program has finished
microos> exec /bin/zcat /etc/greeting.gz
Micro OS: the first port of a program
zlib 1.3.1, MicroFS and ring 3
the bytes of this file were inflated by the library of the guest

microos> exec /bin/spawn
spawn: starting /bin/hello with its own environment

A name with a slash is a path; a name without one is looked up in PATH, where the first regular file with an execute bit wins. The vector of the arguments is the line after the name, with argv[0] the name that was typed, as in Linux.

The port also prints the lines of the task (task: created 'program' ..., x86-64: the program exited with 0); they are left out here. The shell waits: execve returns only when the program has ended (or when it never started), and the port prints the status the program ended with (0 to 255).

The errors, in the order they are met:

Answer Reason
ENOENT the path names nothing
EISDIR it is a directory
EPERM the file has no x bit for the caller (0400 is not a program)
EINVAL the file is not a MOX1 image of version 2, or it names a machine the format does not know
ENOEXEC the image is code for another machine (arch is not k_port_exec_arch())
ENOMEM the image does not fit the window of the port
ENOSYS this machine has no window of programs

A failed execve spends no descriptor of the caller: the file is read through the VFS, not through the table of the task.

The entry on x86-64: int $0x80¶

A program of x86-64 is not a function of the kernel, so the call has to be an instruction of the processor. The vector 128 is a gate of the port:

What Where
the instruction int $0x80
the number of the call rax
the six arguments rdi, rsi, rdx, r10, r8, r9
the result rax (negative is an error)

The registers are the ones of Linux; rcx and r11 are not arguments because the instruction syscall keeps them. The gate opens for ring 3. The processor takes RSP0 from the TSS on the way in, so the handler runs on a kernel stack of the program, not on a stack the program could have pointed anywhere; the handler puts the kernel's thread pointer back, turns the interrupts on, calls ksys_call() and returns with iretq. The table of the calls is in docs/syscall-abi.md and in kernel-abi.md.

A program ends with exit (number 0), not with ret: a return in ring 3 has no kernel frame to land in. The port notices the exit, unwinds to the call that entered it and reports the status (0..255). A program that faults is printed as the program faulted: vector N at 0x..., taken down, and its status is 255; the shell that ran it is alive and answers the next command.

The entry of a program: argc, argv, envp¶

The port enters an image with the arguments of a C function in the registers (ADR 0016):

Register Argument
rdi argc, the number of the words of argv
rsi argv, the vector of the arguments, ended by NULL
rdx envp, the vector of NAME=VALUE words, ended by NULL

The stack is aligned as after a call and its top word is zero, so the C entry is main(argc, argv, envp); a program that returns instead of calling exit faults on address zero. The board has one argument in front of the three - the door of the port - and passes the four in a2..a5 of the windowed ABI; the _start of components/libc/user hides the difference from main. envp is never NULL: a program started without an environment of its own sees the four words of the system - PATH=/bin, HOME=/, USER=root, PWD=/ - because the shell has no export yet.

execve(path, argv, envp) is number 25, and the environment is its third argument, as in POSIX. Both vectors are copied at the edge of the call: at most eight words and 512 bytes each, and a bad one is EFAULT or E2BIG before the file is read. exec /bin/cat /etc/setting passes no environment, and the kernel fills in the one of the system.

The library of a program¶

components/libc/user/ is the library a program is linked against; it is not the library of the kernel, which calls ksys_* and has no address in ring 3:

File What it has
include/ulibc.h the prototypes and the numbers of the calls, from kernel/ksys.h
src/start.c _start: main(argc, argv, envp), then exit; on the board also the door, as the first argument
src/syscall.c int $0x80 on x86-64 and the door of the port on the board; open, close, read, write, lseek, readdir, stat, mkdir, unlink, getcwd, getpid, uptime, execve, exit; the magnitude of a negative result also goes to errno
src/stdio.c printf, puts, snprintf and vsnprintf over a buffer of 128 bytes and write(1, ...); %d %i %u %o %x %X %c %s %p %% and the flags -/0
src/string.c strlen, strcmp, strncmp, strstr, strcpy, strncpy, strcat, strchr, strrchr, memcpy, memmove, memset, memcmp, memchr
src/ctype.c the is* classes and tolower/toupper of the C locale
src/errno.c errno as a global of the program and strerror
src/malloc.c the arena of the program in its bss (ULIBC_HEAP_SIZE), malloc, calloc, realloc, free
src/file.c fopen, fclose, fread, fwrite, fgetc, fputc, fgets, fputs, feof, ferror, fseek, ftell, rewind over a descriptor

The headers a portable source includes (<string.h>, <stdlib.h>, <stdio.h>, <errno.h>, <unistd.h>, <fcntl.h>, <sys/types.h>) are in include/, each one including ulibc.h; a program of the tree includes ulibc.h directly, and a ported program includes the names it knows.

#include "ulibc.h"

int main(int argc, char *const argv[], char *const envp[])
{
    int fd = open(argv[1], ULIBC_O_RDONLY);

    if (fd < 0) {
        printf("cat: %s: error %d\n", argv[1], -fd);
        return ULIBC_EXIT_FAILURE;
    }
    /* ... read and write ... */
    close(fd);
    return ULIBC_EXIT_SUCCESS;
}

The functions return the result of the call, so a negative number is -errno; the same number is also kept in errno, which a portable library reads after the call. The allocation is an arena of the bss of the program, not KSYS_MALLOC: the block of the kernel is memory of ring 0 and a program cannot read it. A program of the library is built by ports/port_x86_64/CMakeLists.txt (the runtime sources are linked with the file of the program, the entry is _start), and the image is a .mox like every other. There is no dynamic linker: each image carries its copy of the library. The recipe of a library of somebody else is docs/porting-programs.md; zcat and zlib are the first.

A regular expression engine: PCRE2¶

/bin/pcre2grep is the one program of the tree with a third-party library under it: PCRE2 10.42, vendored in third_party/pcre2, compiled for the window of the program and linked into its image. The library is 8-bit and interpreted; the JIT is off, and so is Unicode, because a program image is at most 64 KiB (KSYS_MAX_IO) and the Unicode tables alone are about 120 KiB. third_party/pcre2/README.md records the release, the digest and the two optimization passes the image leaves out.

microos> exec /bin/pcre2grep -i h.LLO /etc/setting
hello
the program has finished
microos> exec /bin/pcre2grep -o -g 1 ^hostname=(x86_64)$ /etc/setting
x86_64
the program has finished

The demo is the shape of a grep: one line of the source is one subject, so ^ and $ are its ends, and -o with -g N prints the capture N of every match. A pattern with a space is one quoted word since 1.2.1 (pcre2grep 'a b' file); a character the shell reads as an operator is a debt of the grammar and not of the program. A UTF-8 file is a file of bytes here: a . is one byte, and -u is refused with a sentence instead of silently matching something else.

tests/cases/test_pcre2.c is the gate: a match and a no-match, the groups of a pattern, the anchors of a line, the shape of a UTF-8 subject without Unicode, the errors of the compiler and the values of config.h read back from the library. It compiles the same sources with the same configuration, so the engine on the machine and the engine in the test are one.

The address space and fork¶

A program is a task of the scheduler with page tables of its own:

  • the window is 16 MiB at 32 MiB (0x02000000-0x03000000), mapped onto a physical arena at 64 MiB; the kernel reaches the bytes through its identity map, the program through its own pages;
  • the stack is 64 KiB at the top of the window, with an unmapped guard page below it; the null page is not mapped, so a write to address zero is a fault and not a silent success;
  • the kernel is supervisor-only and out of the reach of ring 3; the program runs with cpl 3 and calls the kernel only through the gate. The kernel image itself is in the higher half (0xFFFFFFFF80000000), and a program's space names that map as it is, without the user bit;
  • fork() copies the page tables, points both copies at the same frames read-only, and the first write of either side faults, copies the 4 KiB page and takes the write bit back. The child returns 0, the parent returns the pid, and waitpid() sees the status.

On a machine without an MMU the same call is a placeholder: the child shares the memory of the parent and re-enters the program, and the port says so. There is no fork() with an address space of its own on the board, and no plan to pretend otherwise.

What a program cannot do¶

  • No ELF and no dynamic linker. The format is MOX1, everything is statically linked, and there are no shared objects.
  • No protected program on the board. The board runs a .mox of Xtensa in two fixed 8 KiB windows of the address space of the kernel (ADR 0018): the image runs, and a bad pointer that reaches the kernel takes the machine down. Protection is the x86-64 port and a processor with an MMU.
  • No libc of the host. A program has the calls of the ABI, the library of components/libc/user and nothing else. The library is not a standard C library: the allocation is a fixed arena of the program and the streams are a descriptor, not a buffer. float and double are those of an image that asks for them (ULIBC_WITH_FLOAT, the port of Lua): it is built without -mgeneral-regs-only, links math.c, setjmp.c and format_float.c. The scheduler saves and loads the XMM and x87 state at every switch, so a program started with fork + execve keeps its own registers beside its parent, and -P of xargs may run several of them at once (docs/debts.md, K9; /bin/fpu2 is the gate of the smoke test).
  • No image larger than 8 MiB. execve reads the file in pieces of KSYS_MAX_IO (64 KiB) into one block of the allocator, up to K_EXEC_MAX_IMAGE (8 MiB); a larger file is E2BIG before a byte of it is read, and the machine holds two copies of the image for the time of the load (debts.md).
  • No descriptor 0 at the prompt. A program is a task with a table of sixteen descriptors of its own, and execve carries the table of the caller: a redirection or a pipe is what fills descriptor 0, and a program started at the prompt with no redirection reads EBADF from it. The descriptors 1 and 2 are the console.
  • No mmap and no brk. A program cannot ask for a range of its own, so the allocator is the arena of its bss and a library that allocates more than ULIBC_HEAP_SIZE needs a larger program or the ranges the kernel does not have yet.
  • No shell export. The environment of every program is the four words of the kernel; a program that wants its own passes one to execve.
  • No protection by SMAP yet. The edge checks the page tables of the caller and then reads the same pages in ring 0; the hardware half of the rule waits for the flags of the processor (SMEP) and the STAC/CLAC window of the copy (SMAP). The higher half is there.

The open rows are in docs/debts.md; the plan is docs/roadmap.md, K4 and K5.
