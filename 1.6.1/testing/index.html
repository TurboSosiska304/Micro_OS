Testing¶

The checks are layered by what they can see. A unit test sees one piece of the kernel; the simulator sees the whole portable system as a process; the x86-64 smoke test sees a bare machine and a processor; the device test sees the board and the chips on it. None of them replaces another.

The commands¶

Command What it proves Needs
make test the host build, the unit tests, the null probe gcc, cmake, ninja
make test-asan the same tests with the sanitizers the same
make test-tsan the same tests under the race detector, on two cores the same
make test-smp the tests of the kernel of two cores (KERNEL_SMP) the same
make test-minimal the host tests with the optional features off the same
make smoke the simulator boots and the shell answers the host build
make coverage the lines of components/kernel and the threshold gcc, gcov, Python
make reproducible two runs of the disk image are the same bytes gcc, cmake, ninja
make x86-build the x86-64 kernel and loader compile gcc, cmake, ninja
make x86-smp-build the same kernel with KERNEL_SMP=ON (ADR 0012) gcc, cmake, ninja
make x86-smoke the kernel boots, runs /bin/hello, the shell answers qemu-system-x86_64
make x86-vga-smoke the VGA screen and the PS/2 keyboard, no display qemu-system-x86_64
make x86-disk-smoke a file written by one boot is read by the next qemu-system-x86_64
make x86-net-smoke the network: ping, UDP, HTTP, httpd and DNS qemu-system-x86_64
make bench the numbers of the machine: the call of the door, fork and exec, a pipe, a file of 16 MiB, the console and a shell pipeline (../bench.md) qemu-system-x86_64, the two builds
make soak one boot of x86-64 for 600 s under the mixed load QEMU, the host build
make soak-host the portable kernel on the host under TSan for 600 s, two cores GCC, TSan, valgrind
make fuzz-long the fuzz of the ABI and the parsers, with a multiplier GCC, ASan
make disk-stress a full volume, fsck -y and two boots (MicroFS, FAT) QEMU, dosfstools, mtools
make board-soak the same session on the board for 180 s, one boot (the gate of a compatibility release; BOARD_SOAK_MINUTES=10 for a change of the flash or the boot) ESP-IDF and a board
make integrity the boundary, the bundle, the partitions, the hygiene clang-format
make ci the list a contributor runs before a push the above, QEMU optional
tools/device-test.sh build, flash and boot the board ESP-IDF and a board

make test: the unit tests¶

make test configures and builds build-host/ and runs ctest, which runs three tests:

  • microos_tests - the unit tests, in tests/cases/, on the framework of tests/framework/ktest.h. There is no external dependency; the tests run inside a real kernel task, so they exercise the task API as well.
  • mkprog - tools/test_mkprog.py, the layout of the image that tools/mkprog.sh writes; it builds tiny objects with the compiler of the host and skips itself when Python is not found.
  • null_probe - the kernel and every portable component linked against the null port. A symbol that portable code takes from a machine by accident is a link error here, on a laptop.

The numeric corpus is tests/corpus/vectors.txt: 512 numbers with the boundary values (0, 1, 255, 65535, 2147483647 and so on) mixed in. A new numeric behaviour reuses it rather than inventing a second list.

make test-asan and make test-tsan are the same tests in build-asan/ and build-tsan/. The board has no debugger, so the host is the place where a wrong pointer or undefined behaviour has to be caught; TSan is the only thing that sees a race, because the host port cannot reproduce preemption.

make test-minimal is the second configuration of the host build (ADR 0010): KERNEL_PSRAM, KERNEL_EXEC, the network components and the second filesystem are off, in build-minimal/. It proves that the sources still build without them and runs the tests that do not need the feature - the cases of exec and of the network are guarded in the source, so the report still says how many checks the small build has.

make smoke: the simulator¶

make smoke runs tools/sim_smoke.py, which boots build-host/ports/port_host/microos_sim with a volume and a store of its own, types a list of commands and checks the transcript: the subsystems, MicroFS, /proc, /dev, the configuration of /etc, the shell and the network. It is the cheapest end-to-end test of the portable system, and it takes a couple of seconds.

The simulator links components/net, so the same HTTP client, clock of NTP and page of the state the board runs over lwIP run there over the sockets of the process. The smoke test starts a small page of its own on the loopback and asks the guest for it with http get, so the path from the shell through the client to a real socket is exercised, not only the parser of a unit test. It does not open a port on the network of the machine: the page lives in the test process, on a port the kernel chose.

make sim runs the same binary by hand, with /tmp/microos-sim.img and /tmp/microos-kv by default. python3 tools/sim_smoke.py --verbose shows every step.

make reproducible: the same inputs, the same bytes¶

The gate of 1.0 asks for an image that two runs build to the same bytes. Three things used to make that fail:

  • the records of MicroFS are stamped with mtime and ctime, and the filesystem took the moment from the clock of the process;
  • kernel_build_id() is __DATE__ " " __TIME__, which changes on every compile;
  • an absolute path of the source tree reached the debug information and __FILE__ of a panic message.

make exports SOURCE_DATE_EPOCH (0 by default, the convention of reproducible builds); make reproducible builds the disk image, keeps a copy, builds it again from nothing and compares the two with cmp, then prints their sha256. What is fixed:

  • tools/mkfs_mfs.c reads SOURCE_DATE_EPOCH (and --source-date-epoch) and gives the filesystem one fixed moment for every record (mfs_set_time_source()); the running machine keeps the wall clock of the kernel;
  • cmake/reproducible.cmake sets __DATE__ and __TIME__ from the same moment and maps the paths of the tree with -ffile-prefix-map, so the kernel id and the debug information no longer depend on when and where the build ran;
  • tools/bundle.sh makes its archive with sorted names, a fixed mtime and the numeric owner 0, and gzip -n; the ESP32 firmware uses CONFIG_APP_REPRODUCIBLE_BUILD in sdkconfig.defaults.

A sdkconfig that was generated before this option existed keeps its old value: the defaults of the tree are read only when there is no sdkconfig. On an old checkout, remove sdkconfig (or set the option in idf.py menuconfig) before the build that has to be reproducible.

SOURCE_DATE_EPOCH changes the bytes of the image on purpose: two dates are two different builds. What is compared is two runs with the same date, the same sources and the same tools.

The board is the other half. The cloud builds the firmware twice, in build/ and build-repro/, and compares micro_os.bin, bootloader.bin and partition-table.bin; it makes the bundle twice as well and compares the two dist/ trees, archive included. Two clean builds of this tree with SOURCE_DATE_EPOCH=0 gave the same three images. A laptop without ESP-IDF can only do the half above, which is why make reproducible is the image and not the firmware.

make coverage: the lines of the kernel¶

make coverage configures build-coverage/ with -DMICRO_OS_COVERAGE=ON (--coverage -O0 -g), runs the unit tests and the simulator, and then tools/coverage_report.py hands every .gcda to gcov --json-format and merges the reports by (source, line), so a source compiled into two binaries is counted once. A line is covered when any of the runs reached it. The report counts components/kernel and fails under the threshold: 70% of lines. This tree met 80.6-80.7% (2581-2584 of 3201 lines) when the gate was added; 70 leaves room for another compiler and another gcov, whose notion of an executable line can differ a little, and is high enough that a regression of the tests is noticed. --path and --threshold move the report to another subtree or another number.

gcov is a part of GCC and no lcov is needed: a machine with the compiler has the report. The counters are removed before the run, so the number is of this run and not of the runs before it.

The x86-64 smoke tests¶

make x86-smoke boots the kernel on a real (emulated) processor: QEMU loads the loader of the port, the loader turns long mode on and copies the kernel, and the kernel prints its banner on the serial port. Then the script types commands into COM1 and checks the answers: the boot, the filesystem, the program of /bin (the execve path, the arguments, the status), the fork with copy on write, the fault of /bin/crash, and the EFAULT of /bin/badptr. The run prints its number of checks, ends with RESULT: PASS, and the count of 1.2.0 is the one of the release run (pending until the integration hands over the tree).

make x86-vga-smoke looks at the other console: it boots with -display none, reads the framebuffer with screendump (a PPM of 1280x800) and the text mode at 0xB8000 with pmemsave, compares the cells with the table of the font, reads the colours of /etc/console and of ls --color, and types with sendkey, so it proves both screens and IRQ1 without a display server. It is a target of its own and not a part of make ci: the monitor of QEMU is a tool a build farm does not have to have.

make x86-disk-smoke gives the machine an 8 MB image on the primary IDE channel, writes a file in one boot and reads it in the next, and runs the programs of the volume (zcat, Lua, bc/dc and the commands of sbase) in both boots. It is the test of the ATA driver, of the MBR parser and of MicroFS on a real medium, and it is also not a part of make ci.

make x86-net-smoke builds the image with -DMICRO_OS_X86_NET=ON, gives QEMU a virtio-net card on its user-mode network and a forward of a port of the host to the guest, and checks the whole contract of the port over the wire: the device and its MAC, ping of the gateway, a UDP exchange with an echo server of the host, an HTTP GET of the client of components/net, the stream of wget, TLS 1.3 and 1.2 with a wrong name and a wrong authority refused, the install of a signed package over HTTPS, the page of the state served by the guest through hostfwd, and a name the resolver answers twice (the second from the cache). Like the other two it is not a part of make ci: it opens a port on the loopback and needs the user-mode network.

make x86-iso-smoke boots the BIOS ISO with -cdrom and nothing else - no -kernel, no -initrd, no disk - and checks the loader, the signature of the kernel, the mount of the root module and the shell with /bin. It is the definition of "the ISO boots" and it is not a part of make ci.

make integrity: the boundary and the hygiene¶

tools/integrity_check.py checks what a compiler cannot:

  • the layers: the kernel includes only the kernel, a portable component no platform header and no k_port_* call, and a port implements the whole contract of kernel/port/*.h;
  • the bundle in dist/, when there is one: the sums and the images;
  • the partition table: partitions.csv against the flash size and the build;
  • the budget of the image: the firmware fits its 2 MB slot;
  • the features (ADR 0010): a flag that is off leaves no symbol in the map of the ESP-IDF build and no library in the host build;
  • git: the objects, through git fsck --strict;
  • the hygiene of the sources: UTF-8, LF, no trailing whitespace, no tabs, 100 columns in C, and clang-format when it is installed.

--skip-format --skip-git and --expect-version <version> are the useful options when a release is prepared; --verbose names every check. The release workflow passes --expect-tag <tag> instead of the version: the numbers and the suffix of the kernel must be the tag's, so a release_candidate that forgot its -rc1 fails the check instead of calling itself a release.

make ci: the local half¶

build, test, test-asan, test-tsan, test-smp, smoke, coverage, [x86-smoke], reproducible,
integrity

x86-smoke joins the list when qemu-system-x86_64 is on PATH and is skipped with a message when it is not: a missing optional machine must not fail a run. coverage and reproducible are blocking: the first refuses a kernel below 70% of lines, the second refuses two images that differ. make ci does not build the firmware of the board (that needs ESP-IDF) and does not run the VGA or disk smoke tests or the device test.

The cloud repeats the list on every push to mainline and release_candidate and adds what a build farm has: valgrind over the tests, the firmware build, the bundle, and x86-smoke. The local half and the cloud half are close but not identical; docs/debts.md keeps the difference as a debt.

The device test¶

tools/device-test.sh                  # auto-detected port
tools/device-test.sh /dev/ttyACM0
CONSOLE_SECONDS=60 tools/device-test.sh /dev/ttyACM0

The script finds ESP-IDF ($IDF_PATH, ../esp-idf, ~/esp/esp-idf), builds, flashes, reads the console for CONSOLE_SECONDS (30 by default) and prints RESULT: PASS when the self test, the hardware doctor and the shell came up. It is outside CI: no runner has the board. A release is gated on it by hand.

tools/console.py reads the console without flashing; tools/stream_console.py is the interactive version. Both need pyserial, which the ESP-IDF Python environment already has.

Adding a test¶

A new case needs four touches (the same list as in AGENTS.md):

  1. tests/cases/test_<thing>.c;
  2. the void test_<thing>(void); declaration in tests/include/tests/tests.h;
  3. the call in run_tests() in tests/src/main.c;
  4. the file in add_executable(microos_tests ...) in tests/CMakeLists.txt.

Kernel behaviour without a test is unfinished work. A test that needs real hardware is a sign that platform and portable code got mixed: the kernel tests run on the host, and the board is checked by the device test and by the smoke tests of its port.

The fuzz of the ABI and of MOX1 has a deterministic seed (tests/cases/test_fuzz.c); the numbers of the campaign are in the next section, and the records of MicroFS are fuzzed there too.

The campaign of 1.0¶

The gate of the release is written in docs/releases/1.0.md: one session runs 600 seconds under a mixed load without a bug, and the session is one boot. A loop of twenty-five short boots is a useful smoke test of the tools, but it is not the gate: a leak, a lost wakeup or a slow corruption needs the same machine to stay up.

The campaign is the four tools below, on the two machines and the host substrate:

unit soak fuzz stress
host make test, make test-asan, make test-tsan make soak-host (TSan, 600 s) make fuzz-long valgrind, inside soak-host
x86-64 make test (the same sources) make soak (one boot, 600 s) make fuzz-long make disk-stress
board tools/device-test.sh make board-soak (180 s) — fsck in the board session

make ci does not include the campaign: ten minutes of QEMU and a board do not belong to a push. The campaign runs on a release candidate and its report is attached to the candidate.

One boot, 600 seconds: make soak¶

make soak                      # 600 s, one boot of the x86-64 machine
make soak SOAK_MINUTES=1       # the smoke test of the tool itself

The target builds build-x86-net (the port with the network and its disk) and a full volume (tools/soak_image.py), then tools/soak.py boots the machine once and types a cycle of commands until the clock says stop:

  • the shell: uname, uptime, free, df, ulimit, ps, mount, tree, fsck, kill of a pid nobody has, sleep;
  • every program of /bin through exec: hello, cat, echo, ls, wc, grep, head, mkdir, rm, pwd, spawn, fork, signals, nx, badptr, crash;
  • pipelines and redirections: ls /bin | wc -l, cat < f | wc -l, echo x > f, echo y >> f, and a read of the file back;
  • the filesystem: a directory, a program's rm -r, files written, appended and removed; once per boot the volume starts with no free block, one write is refused with ENOSPC, the filler leaves, fsck -y repairs and the volume is used again;
  • signals: exec /bin/signals and Ctrl+C typed into the console while the program runs;
  • the network: ping 10.0.2.2, the HTTP client against a page of the process, the httpd page reached through hostfwd, and DNS when this host can resolve a name.

The direct form has the same options: tools/soak.py --minutes 1, --seconds, --seed, --keep-logs, --no-net, --hang-seconds. --iterations N is the other mode: N short boots, one cycle each, with the average boot reported. It is for the days before the higher half; the gate is the single 600-second session.

A session fails on any of:

  • a Panic, a Guru Meditation, a triple fault, Rebooting, a failed assertion or *** ERROR in the console;
  • QEMU going away before the clock ends (a reset is the end of the boot);
  • the console silent for --hang-seconds (30 by default), or a command that does not answer inside --timeout;
  • a command of the load whose answer lacks the word it must have;
  • a heap that lost more than --mem-drift-kb (16 KB by default), a shell that holds memory at rest, a changed descriptor limit, or a task table that grew;
  • a difference between the free/ulimit/ps/df samples before and after the load. The numbers are printed in the report.

NTP is skipped with a line of the report when the process cannot bind UDP 123: the kernel asks 10.0.2.2:123, which QEMU maps to the loopback of the host, and a laptop has no privilege for the port. That is a skip and not a pass; a runner with CAP_NET_BIND_SERVICE (or a network namespace) runs it.

The transcript of a failed session is written to build-x86-net/soak-logs/ (and --keep-logs writes the one of a pass); the report prints the path.

The host half: make soak-host¶

make soak-host                   # TSan for 600 s and one valgrind run
make soak-host HOST_SOAK_MINUTES=1

tools/host_stress.c is the load: four tasks of the host port at once, each allocating and freeing blocks of kmm, making pipes, creating, rewriting and removing files, and forking a child that exits (task_fork_shared). The version built in build-tsan is the one that matters: the host port stands in for the critical section with a mutex and cannot show preemption, so TSan is the only reader of a race here.

The tool fails on a WARNING: ThreadSanitizer (and prints the location it names), on a stress that stops printing (a deadlock), on a run that ends before its time, on a block the allocator still holds, on a task left in the table, or on a definite leak of valgrind. One run of 5 seconds under valgrind is a part of the target; --skip-valgrind is for a machine without it.

The first campaign of this tree named a race that the shorter tests never saw: g_last_error in components/kernel/src/vfs.c is written by every VFS call from the tasks' threads and is read by nobody. It is an open debt in docs/debts.md; until it is closed, make soak-host fails, which is the correct answer of the tool.

The fuzz: make fuzz-long¶

make fuzz-long                                # 20x the iterations, seed 0
make fuzz-long FUZZ_ITERATIONS=200 FUZZ_SEED=7

The suite is the ordinary one in the sanitizer build; the campaign only moves two numbers of tests/cases/test_fuzz.c through the environment: KTEST_FUZZ_ITERATIONS multiplies the loops and KTEST_FUZZ_SEED changes the seed of the MOX1 and MicroFS streams. The binary still runs every case, so the ABI edge (test_ksys), FAT, ext2 and the network are exercised in the same run. A long run is repeatable: the same seed and the same multiplier give the same sequence on every machine.

The disk: make disk-stress¶

tools/disk_stress.py boots the image twice. The first boot finds a full volume (ENOSPC), removes the filler, repairs with fsck -y, writes, appends, makes and removes a directory, and leaves a file for the second boot. The second boot checks the volume, reads the file, and runs and removes again. The verdict is that the volume is either whole or made whole by the repair: fsck says the volume is consistent, or 0 problem(s) after the repair, and never a problem after it.

MicroFS is checked on build-x86; FAT is checked in a second partition of an image of build-x86-fat (the port with MICRO_OS_FS_FAT32=ON), filled with mcopy and repaired with fsck fat -y. Those two halves need mkfs.vfat and mcopy; when they are not installed the FAT half is reported as skipped, and --require-fat turns that skip into a failure for a runner that must have them.

The board: tools/board_soak.sh¶

make board-soak                             # build, flash, 180 s
tools/board_soak.sh --minutes 10            # the long session of a release
tools/board_soak.sh --minutes 1             # the tool itself
tools/board_soak.sh --no-build --no-flash   # the firmware already there

The gate of the board of 1.2 is three minutes: from 1.2.0 the board is the compatibility port of ADR 0018, the changes of the release are small, and ten minutes of the same cycle would not prove another thing. A change of the flash, the boot or the volume asks for BOARD_SOAK_MINUTES=10 and the long session of the releases before 1.2.

The script does what tools/device-test.sh does (finds ESP-IDF, builds, flashes) and then tools/board_soak_session.py resets the board once and spends one boot with it: exec /bin/hello with arguments, cat of a file written by the shell, files appended and removed, mkdir/rm -r, the foreign image's exec format error, fsck, telnet on/off, wifi status, display rotate, mfetch, modules, sleep, abi, ps and ulimit. A panic, a Guru Meditation, a backtrace, a reboot, a silence or a descriptor/memory/volume/task drift beyond the small allowance fails it. The report prints the heap, the free blocks, the descriptors and the tasks before and after, and the drift the run allows.

Reading a result and the levels of a bug¶

A pass is the last line RESULT: PASS 600s (the x86 and host sessions), RESULT: PASS (N short iteration(s)) for --iterations, or RESULT: PASS 600s from the board. The report above it is the evidence: duration, boot, cycles, commands, memory/descriptors/tasks before and after, and the first failures with the line of the answer. Attach it to the candidate with the uname of the build, the command, the seed, the logs of build-*/soak-logs/, and the lines network ... ntp ... dns ... that say which halves actually ran.

The campaign classifies what it finds:

  • L1 — a crash, a loss of data or a security hole. A panic, a reboot, a triple fault, a corrupted volume that fsck -y cannot repair, a file that disappears, a task that faults where the kernel should have answered EFAULT. Always a blocker.
  • L2 — a feature is broken. A command of the load that must pass and does not, a fsck that leaves a problem, a fork or a signal with a wrong answer, a leak that grows with the load. Always a blocker.
  • L3 — an edge or a rare race. A TSan warning, a window that needs a seed and many iterations, an ENOSPC path that leaves a surprise. A blocker for 1.0 unless it is recorded as a debt with its next step and its workaround; the g_last_error above is such a case.
  • L4 — cosmetic. A line of output, a message of the log, a spelling. It changes no result and may stay at the release.

The four levels are the same on every machine. A failure of a tool that has not been run (a skipped network or a missing mcopy) is not a pass: the report says skip, and the release notes say which halves were skipped.
