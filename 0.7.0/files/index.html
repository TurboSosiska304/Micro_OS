Files¶

Micro OS has one filesystem of its own, MicroFS, two virtual filesystems, and a FAT12/16/32 volume it can both read and write. The root / is MicroFS on a block device; /proc and /dev are generated by the kernel. Everything a person writes at the console lands in MicroFS unless a FAT volume is mounted, and the configuration of /etc has a second copy in the store of the port, which is why a format does not have to lose it.

The layout of the volume, the sections and the flags of a record are described in docs/memory.md; this page is about using it.

The tree after a boot¶

The simulator, right after a boot (the board adds /log, x86-64 adds /bin):

microos> tree /
/
|-- etc/
|   `-- init.d/
|-- proc/
|   |-- version
|   |-- uptime
|   |-- meminfo
|   |-- tasks
|   |-- modules
|   |-- self/
|   |-- 1/
|   `-- ...
`-- dev/
    |-- tty0
    `-- ...
Path What it is
/ MicroFS on the volume of the port
/etc the configuration: a file name is the key, its content the value
/etc/init.d the scripts of the init process, one command per line
/etc/fstab the volumes the boot mounts after the root, when the file is there
/proc the kernel: version, uptime, meminfo, tasks, modules, one directory per task
/dev the devices: tty0, null, input and the ones the port adds
/log on the board: start.log, the log of the boot
/bin on x86-64: the programs the boot writes (hello, crash, fork, badptr)

ls prints the names of a directory, one per line; -l adds the mode, the owner, the size and the date, and -a the two names . and ... tree draws the levels below a path, and stat is the detailed view of one object.

MicroFS¶

MicroFS is a consumer of blocks, not of a flash chip: the device under it is described by kernel/blockdev.h and registered by the port. On the board it is the mfs partition of the internal flash (flash0, 5.75 MB); in the simulator a file of the host (file0, 512 KB by default); on x86-64 the first partition of the ATA disk (ata0p1) when one is attached, and a volume in the RAM (ram0, 512 KB) when it is not.

A volume has three sections and a block is 1 KiB:

Section Holds
DATA the content of the files
META the table of the records and the map of the free blocks
INFO the header of the volume and the root record, in the last erase sector

A record of today is 32 bytes: it keeps the type of the object, its mode and its owner in the upper bits of flags, and the two moments of a change (mtime and ctime) in the seconds of Unix after them. A volume of an older release has 16-byte records with no room for a time and mounts unchanged; its objects report zero, which is "unknown" (ADR 0013). The formatter asks for 256 records (MFS_MOUNT_RECORDS) and sizes META from the volume; the capacity is fixed at format time and cannot grow later. There is no journal: fsck reports the first problem it finds and does not repair, and a power cut in the middle of a write is a risk the tree knows about (docs/debts.md).

The calls of the filesystem take one recursive lock, so two tasks can use the volume at the same time without corrupting it: each open file keeps its position in its descriptor, and the volume itself is one piece of state behind a mutex. The codes of the filesystem are translated into the codes of the system calls in one place, components/mfs/src/mfs_vfs.c.

Working with files¶

microos> write /hello.txt one two three
14 byte(s) written to /hello.txt
microos> cat /hello.txt
one two three
microos> mkdir /data
microos> df /data
blocks: 482 of 487 free (1 KB each)
inodes: 1274 of 1279 free
microos> rm /hello.txt

write replaces the file and appends a newline; the text is one line of at most 127 bytes. rm removes a file, not a directory, and there is no -r. df prints the free blocks and inodes of the filesystem of the path.

stat shows the mode, the owner and the size; chmod and chown change the first two. A program asks for the moments of a change with statx (number 26 of the ABI) and microos_statx() in the library; a volume of version 1 has none, so the two times come back as zero and not as 1970. The rules are in kernel-abi.md and in docs/syscall-abi.md: one user (uid 0), no root bypass, and a zero mode means "this record predates the modes", so chmod 000 is refused.

mkfs and fsck¶

microos> mkfs -y
mkfs: the volume is formatted

mkfs -y unmounts /, formats the volume and mounts it again. Without -y it does nothing but print its usage; with -y everything in MicroFS is gone. It is registered on the board (main/src/main.c) and in the simulator (ports/port_host/src/sim_main.c); the x86-64 port has no such command and formats a blank volume at the boot instead.

fsck is the read-only check:

microos> fsck
fsck: 0 file(s), 3 directory(ies), 484 of 487 block(s) free
fsck: the volume is consistent

A broken volume prints N problem(s), the first: ... and the command exits with an error. fsck: no volume is mounted means that / is not MicroFS on this machine at the moment.

The second filesystem is checked by the same command, by the point or by the device: fsck fat /mnt/fat reads a volume that is mounted, fsck fat sd0 mounts the device for the length of the walk. The report names the cluster, the directory or the copy of the table that is wrong, and the counters say how much of the volume is free and how many clusters no chain names. It is read-only as well, and a volume with more than 65536 clusters is refused with a message. See the second filesystem.

/etc and the store¶

The files of /etc are the configuration of the system, and each file is one key of the key-value store of the port (NVS on the board, a file per key in the simulator). The boot restores the files that are missing and saves the ones it finds; the file wins when the two disagree.

microos> write /etc/setting hello
microos> config sync
config: 0 file(s) restored, 1 saved
microos> config
setting=hello

This is why mkfs -y does not take the settings away: the store survives the volume. idf.py erase-flash destroys both. In the simulator the store is the directory MICROOS_KV_DIR (/tmp/microos-kv by default), and a run with a volume of its own should have a store of its own too.

/etc/init.d¶

Every file of /etc/init.d is a script of the init process: one shell command per line, # starts a comment, and each script runs in a task of its own. The directory is created at the boot when it is missing. The commands are the ones of shell.md, so a script can only use what the machine registers:

microos> write /etc/init.d/clock date
microos> reboot

Disks and partitions¶

The kernel has a portable parser of the partition tables (components/kernel/src/partition.c, ADR 0008): it reads the MBR or the GPT in the first sectors, holds every entry against the size of the disk, and registers a child device named after the parent plus p and the number of the entry. A child adds the first sector of its partition to every request and refuses what runs past its end.

Device Where What
flash0 board the internal flash; the mfs partition mounted at /
file0 simulator a file of the host
ram0 x86-64 memory, 512 KB, not persistent
ata0, ata0p1 x86-64 the IDE disk and its first partition
vd0, sd0, nvme0n1, mmcblk0 planned virtio, AHCI, NVMe, SDHCI

Three rules of the layer matter at the console:

  • the parser never writes to the medium: a broken table is a refusal, not a repair;
  • a disk without a table is not a volume, and there is no "the whole disk is the filesystem" special case;
  • what a filesystem sees is a device, so MicroFS on ata0p1 does not know that a partition table exists.

The x86-64 disk is a raw 8 MB image, made by tools/x86_disk_smoke.py --mkimage and kept in build-x86/disk.img; what is written to it survives a reset, which make x86-disk-smoke proves with two boots. See docs/ports/x86_64/README.md.

The second filesystem¶

The VFS knows filesystem types (ADR 0009): vfs_register_type() puts a name and a mount function in the table, and vfs_mount_type(point, "fat32", device) mounts a type on a point. MicroFS is one type; components/fs_fat32 is a second one, FAT12/16/32 with the long names, the fixed and the cluster root and the subdirectories.

The volume is read and written. It speaks the whole life of a file: open with O_CREAT, O_TRUNC and O_APPEND, write, close, unlink and mkdir, on FAT12, FAT16 and FAT32 alike. The clusters are taken from the free map and given back on removal, both copies of the table are kept together, and a long name that is created gets its run of long-name entries with the checksum of the generated 8.3 name. df works on it (statfs walks the table), and so do the shell commands that go through the VFS:

microos> write /mnt/sd/note.txt hello
6 byte(s) written to /mnt/sd/note.txt
microos> cat /mnt/sd/note.txt
hello

mount and /etc/fstab are still ahead; an image that wants a FAT volume asks for one in its boot, after fat_vfs_register_type(). On the board the component is behind CONFIG_MICRO_OS_FS_FAT32, off by default; the host tests always build it.

What a FAT record cannot carry is still absent: stat answers mode = 0 and owner 0, chmod and chown are ENOTSUP, and there is no time of the change. unlink removes a file or an empty directory and refuses a directory that holds an entry with ENOTEMPTY; rename is not a call of the VFS yet. The mount does not ask whether the medium can be written: a card with its physical write switch on mounts and is refused at the first write, because reading it is still useful.

Writes go to the medium before the call returns and the device is synced when it has a sync of its own, but there is no journal: a power cut in the middle of a write can leave a cluster no chain names or a half-written entry. fsck fat <point|device> walks the volume read-only and names the first problem, exactly as fsck does for MicroFS: the boot sector and the BPB, the copies of the table, the chains, the entries and their long names, and the clusters no chain names. It does not repair: the clusters it calls lost are still lost after it returns. That is the price of writing a volume this kernel did not format, and it is written in docs/debts.md.

The host test mounts MicroFS at / and FAT at /mnt/fat at the same time, reads and writes through the VFS, and mounts the same image again after an unmount to prove the bytes are on the medium. On a board or an x86-64 image the type is registered at the boot when MICRO_OS_FS_FAT32 is on; the board has it off by default.

MicroFS registers its own type (mfs) as well, so the volume of the flash can be named like any other.

Mounting a volume¶

mount without a word lists the points of the tree, in the order the boot mounted them. With the three words device point type it mounts a volume of a registered type; umount gives the point back:

microos> mount
/
/mnt/fat
microos> mount ata0p1 /mnt/fat fat32
mount: ata0p1 is mounted at /mnt/fat
microos> ls /mnt/fat
...
microos> umount /mnt/fat
umount: /mnt/fat is out of the tree

The point need not exist in the filesystem above it, and neither does its parent: a mount is shown in the listing of the directory above, which is how /proc, /dev and /mnt/fat appear in ls. What is already there has to be a directory, so a mount over a file is not a directory; a point that already holds another filesystem is device or resource busy, and a point with a mount below it stays until the smaller one leaves. / is the exception: the mounts of /proc and /dev do not live on its volume, so mkfs -y may take the root out while they stay.

/etc/fstab¶

The boot mounts the volumes of /etc/fstab after the root, when the file is there. Each line is device point type [options], # starts a comment and an empty line is not a line:

# the volumes of the machine: the device, the point and the type
vfsfat0  /mnt/fat  fat32

# a line of Linux with the options of a mount is read as well
ata0p1   /mnt/card fat32  defaults

Only defaults is a known option for now: an option that the kernel cannot honour (ro, a comma-separated list) is named in the log and its line is skipped. A line that does not mount for any other reason - a type the image does not have, a device that is not there, a point that is busy - is skipped the same way: a broken table does not stop the boot, and the shell still starts with mount -a to read it again after a repair.

The file lives in MicroFS, so it is one of the files of /etc that the store of the port keeps across a format. A volume mounted at the console is not written back to the table: mount changes the tree, not the configuration.

What is not there yet¶

  • No ext2, and no journal under a FAT write. A FAT volume is written without a log; a second FAT volume and a mount of a card at runtime are ahead, and fsck fat only reports: a repair of the clusters it calls lost is the next step.
  • No access time, so statx has two moments of three; a read does not rewrite a record.
  • The options of /etc/fstab are not acted on: only defaults is accepted, and a volume mounted at the console is not written back to the table.
  • MicroFS is one volume at a time: the type mfs mounts the medium the filesystem keeps, so a second MicroFS volume is a change of the filesystem.
  • No journal and no repair: fsck names the first problem of MicroFS and fsck fat the first problem of a FAT volume; neither fixes it, and FAT has no repair of its lost clusters.
  • No mv, no cp: rm -r and the other commands of the shell are there.
  • One user, so the owner of a file is a number that is stored and checked but not a second party.
  • No mv, no cp: rm -r and the other commands of the shell are there.
