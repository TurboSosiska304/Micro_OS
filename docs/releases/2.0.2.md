# Micro OS 2.0.2

> 2.0 on the medium a person boots. The desktop works when the root is
> read-only, the screen goes to the video memory in one write-combining burst
> instead of a transaction per pixel, and the gates boot the image the release
> hands out instead of a disk this tree writes for itself.

2.0.0 was the machine of its user, and it was tested on a disk image the tree
writes: a writable root, a framebuffer that is ordinary RAM in the emulator.
The first stick of the release met a real laptop and found three defects that
no gate could see, in the first minute, on the boot screen. 2.0.2 is those
three defects and the gates that would have caught them.

## The desk on a read-only root

The stick mounts `boot0p1` read-only by the rule of ADR 0041, and `wm` keeps
the pixels of a window in a file of `/tmp`. On the laptop of the owner the
result was a desktop that said it was up and had no window:

```
root: boot0p1 cannot open its writes, the root stays read-only
wm: no file for the pixels of a window
wm: /bin/term exited with code 138
```

`/tmp` is a **ramfs** now when `/` was mounted read-only. A file takes 1 KiB
blocks from the kernel allocator as it is written and gives them back when it
is removed; the last mebibyte of the heap (`RAMFS_RESERVE_KB`) is out of reach
of a write and answers `ENOSPC`, so a full `/tmp` is a full `/tmp` and not a
dead machine; `df` names the space honestly; `unlink` of an open file keeps
the blocks until the last descriptor closes. The board does not build the
filesystem at all: it has about 100 KB of SRAM and no window to draw in.

The gate of this is `x86-iso-desk-smoke`: it builds the ISO - read-only by
design, the same root the laptop had - boots it, and checks the line
`x86-64: /tmp is a ramfs, the root is read-only`, then `exec /bin/wm`, `Alt+T`,
`help` in the terminal and `Alt+F4` back to the prompt.

## The framebuffer that was neither cached nor combined

Every write of four bytes went to the video memory as one uncached transaction
over PCIe, and a glyph of 8x16 was 128 of them. The console printed five to ten
characters a second after the kernel took the screen, and `wm` drew at the same
speed. `IA32_PAT` entry 5 is write-combining now, set on every core, with the
window's PTE `0x800000000000108b`; the UEFI GOP window, which was uncached at
all, gets the same policy; a machine without PAT gets write-through
`0x800000000000008b` and the same picture. A glyph is drawn as one row of eight
bytes in a buffer and copied with one `memcpy`, and the UEFI conversion copies
128 pixels at a time.

The gain cannot be measured in QEMU: its video memory is RAM and TCG does not
model the write-combining bus. The release therefore gates the **policy** - the
values read back from the PAT, the PTE and the MTRR - and the owner's laptop is
the machine that measures the speed.

## The machine we test is the machine we hand out

Two smokes were green for months because they ran a machine nobody ships: the
desktop was started from `init` on a writable disk, and the frame check assumed
the banner was the first line of the screen, which stopped being true the day
the wire printed its own lines. `x86-vga-smoke` starts the desk from the shell
and searches the frame for the banner; `x86-iso-desk-smoke` boots the medium of
the release. `mfetch` says what the machine is - the version, the machine, the
cores in use against the cores the firmware reported, the memory and the disk
with a bar - instead of the build id and the number of allocations.

## What this release does not carry

* **One core.** `KERNEL_SMP` stays off: eight cores work (the log says
  `8 in use`, the gates of two cores pass), but the shell of the soak stops
  answering once in a few runs on eight cores and the cause is not named yet.
* **The clean end does not switch the laptop off.** The write of S5 is
  followed by a page fault in `memcmp`, and the machine stays on.
* Both are the work of 2.0.3, with `docs/debts.md` and `docs/plan-2.0.2.md`.
