# Micro OS 2.4

> The disk is written, the copy is read back, and the machine that cannot trust
> its many cores runs on one.

2.3 taught the installer to read a disk and refuse a bad table before any write.
2.4 teaches it to write: append one partition in a gap it already named, format
it, copy the running system, and prove the copy with a SHA-256 manifest. It also
closes a class of formatter and diagnostic defects that had made the USB gate
lie, and it names the SMP memory corruption that keeps the many cores out of the
release.

## The installer writes, copies and verifies

The x86-64 installer keeps the 2.3 contract: dry-run is the default, the GPT is
read before it is touched, and a damaged, inconsistent or hybrid table is
refused before any write. After an exact confirmation it appends one Linux data
partition in the gap the plan named, verifies both GPT copies, and refuses to
touch a live or busy disk.

L3 formats that partition as ext2 or MicroFS, mounts it, writes the tree a boot
expects, and records the install in `/etc/install` and `/etc/volumes`. The
format is the real one: `ext2_format()` writes a volume the ext2 driver can
mount, and `mfs_format()` writes a MicroFS volume at its own grain. The empty
mount points of the tree are created; the four files the installer owns are not
overwritten with defaults.

L4 copies the running system, not a second definition of it: the kernel of boot
module 0 goes to `/boot/kernel`, the live `/bin` and `/etc` are copied with
their modes, and the files the installer already wrote on the new volume stay in
place. Every copied file is recorded in `/etc/install.manifest` as a logical
path, its byte count and its SHA-256; the hash of the manifest itself is written
to `/etc/install.manifest.sha256` and printed on the console.

After the copy the installer syncs the manifest, unmounts the volume, closes the
write door of the disk, and mounts the volume read-only through `vfs_mount_type()`
with no writes allowed. Only a file that matches the size and the digest of its
manifest line passes. A mismatch names the file and the two hashes and the
command ends with a failure that leaves every byte of the volume as it is;
"installed, verified" is printed only after the last file passed. `install
--verify` repeats the read-only check without writing anything.

The gate covers the copy and the corruption case: `tools/x86_install_smoke.py`
runs an ext2 install and a MicroFS install on a separate 32 MiB disk, checks the
tree, the manifest, the manifest hash, a clean `--verify`, and a second boot
after one byte of a copied file was changed on the medium. The damaged copy must
fail with `MISMATCH /etc/corrupt-me` and write nothing.

## The formatter tells the truth

The x86-64 libc formatter in `ports/port_x86_64/src/libc_shim.c` now honours
length modifiers in its vararg path: `%lu` and `%llu` had read a 32-bit argument
and printed the low half of a 64-bit value. The fix makes 64-bit sizes, sector
counts and addresses print as the values they are.

The diagnostic helpers were given the format attributes they were missing:
`klog`, `kshell_printf`, `wdg_printf` and the `pkg_say*` helpers now carry the
attributes that let the compiler check their format strings against their
arguments. The warnings that fell out of that check were fixed in the same pass.
`ports/port_x86_64/src/port_x86_64_task.c` clamps truncated diagnostic output
before writing it, so a long line is cut instead of overrunning the buffer it is
written into.

The visible consequence is the USB gate: `usb-smoke` is 66/66.

## The watchdog names the hang

The hang watchdog (merged as `feature/hangwatch`) gives a stuck machine a voice.
An NMI or vector `0x14` path dumps the state into the gates instead of leaving a
silent timeout. The watchdog records where the CPU was, which lock it held, and
the provenance of the stop. The gate tooling can turn a red hang into a dump that
names the place, which is the difference between "answered nothing" and a defect
report.

Signal provenance is recorded with the delivery: a signal carries `si_code`, and
the path that killed a task can say who sent it. `SIGSTOP` is no longer lost when
a task arms its first sleep; a stop that arrived in that window is kept and the
task stops instead of running past it.

## The GPU work moves, carefully

The AMD lane adds VRAM buffer-object groundwork and a `bufmap` path: buffer
objects can be allocated, filled, read back, freed, listed and flipped through
the BAR0 aperture. The GPU probe and the AMD path report the memory they found;
the write test stays guarded. The Intel lane adds GGTT mapping and display-enable
work: `ggtt-map` and the GGTT test expose who owns which entries, and the plane
path can be enabled through the documented sequence. Mode setting and backlight
remain a plan, not a register write.

## What this release does not carry

* **`KERNEL_SMP` is off by default.** Eight cores work in QEMU and on the
  laptop, but under load user program memory is corrupted: PTEs are valid, an
  operand register holds garbage, and 3 of 6 runs of the 15-stage pipeline fail.
  A machine that occasionally damages the memory of its programs is not a
  release. The single-core default is the honest one; the many cores come back
  with the fix. Build with `KERNEL_SMP=ON` for the SMP work, or follow
  `feature/pipe15`.
* **The install does not boot from the installed volume.** L4 copies the system,
  writes the manifest, verifies it on a read-only mount, and `install --verify`
  repeats the check. The loader/ESP files, the NVRAM question and booting the
  installed disk as a normal writable root (L5/L6 in the install plan) are not
  done. A person can install and verify, but cannot yet boot the result as the
  machine's own disk.
* **Mode and backlight are only a plan.** The Intel mode/backlight plan is
  written; the registers are not touched.
* **WiFi has no `ALIVE` on the live card.** The 8265 path reaches stage 2 and
  the contract is recorded, but the radio is not yet `ALIVE` on real hardware.
