# Micro OS 2.1

> The thaw after the major. The defects 2.0 left, the debts of the list, and the
> first release whose gates boot the medium a person boots.

2.0 was the machine of its user; 2.0.2 put it on the stick. 2.1 is the release
that makes the machine **answer and hold**: the terminal is a file with process
groups, the machine keeps its own log and never writes a password into it, the
USB controller enumerates what is plugged into it, and the GPU says what it is -
with an AMD probe that reads the memory controller and an Intel one that walks
the page tables of the display.

## The terminal is a file

`term`, `login` and `su` shared one tty through three different pieces of
plumbing, and Ctrl+C did what the plumbing happened to allow. Now the tty has a
session owner and a **foreground process group**: `getpgid` (52) and `setpgid`
(53) are in the ABI, a program started from the shell runs in its own group, and
Ctrl+C is a `SIGINT` to that group and never a byte to the reader.

The defect this closed was serious: the shell inherited init's process group and
put the terminal's foreground group on it, so **a signal aimed at a program could
take down the shell and init** and leave the console dead - the owner met it as
`grep` and as `kilo`. A program that dies now ends alone; the shell reports the
code and keeps its prompt.

## The machine keeps its own log

`/etc/bootlog.log` is the boot of this start, and the previous one stays as
`bootlog.1.log`, so a machine that does not start still leaves the attempt
before it. `run.log` is the session. Both rotate at 64 KiB, both are written in
batches by the init loop, and the log is closed **before** the volumes leave, so
a clean end is not held up by its own writer.

**A password is never written.** The rule is structural: `session_read_line`
with `secret=true` hides the input from the log, and `login`, `su` and the
telnet authentication go through it. A read-only root keeps the log in RAM and
says so instead of pretending.

## USB enumerates

K25 was a port that reported five devices and enumerated none: the driver added
the port register base twice, so every read came from the wrong register
(`PORTPMSC` instead of `PORTSC`) and every port looked empty. The base is one
number now, the reset follows the specification (`PR` once, wait for `PRC`,
`PED` and `PLS=U0`, USB2 in `Polling` is reset while USB3 finishes training),
and every wait has a boundary and a line in the log.

## The GPU answers

One interface for both vendors, and three honest answers: `ok`, `unknown` (a
card of a known vendor that we do not know) and `skipped` (no card of ours).

* **AMD** reads the memory controller: exact VRAM (`8192 MiB` on the RX 570),
  the channel map, the L1 TLB configuration. `gpu vramtest` reads the display
  pipe registers, finds the scanout, and refuses to write anywhere that
  overlaps it or the first 16 MiB; with `--write` it writes a pattern, verifies
  it and restores the original bytes.
* **Intel** walks the GGTT (through the alias at `BAR0+8 MiB`), prints the
  framebuffer, borrows a page of the GTT for a read/write test, and can point
  the plane at a copy of the frame with `gpu flip --yes`, verifying the copy
  and restoring the old surface.

Facts about the registers come from the drivers of Linux: `amdgpu` is MIT and
its files are named in the header of ours, `i915` is GPL and only its knowledge
is used - the code is written here.

## The frame path

Phase A of the GPU plan: the desk composes into a RAM back buffer and sends one
batched blit per frame, with damage rectangles, a glyph atlas and word copies.
The policy of the memory (write-combining of 2.0.2) is unchanged and still read
back by the smoke.

## What this release does not carry

* **Eight cores.** `KERNEL_SMP` stays off. The pilot of 1.3 works, and the
  gates of two cores pass, but on eight the shell still stops answering in about
  one soak in four: two causes were found and fixed (the boot context held the
  filesystem lock while a core yielded in its idle; a log line could be split in
  two writes), a third - the shell asleep while its child is a zombie - is still
  open. A machine that freezes once in a few runs is worse than a slower one.
* **The page cache of 2.2.** It is written, it made `file_read` slower by 216
  and then faster than the base after the fix, and it is not here: `fsck` finds
  the volume inconsistent after a writeback. Durability that corrupts a volume
  is not durability.
* **A GPU that drives the laptop.** The Intel flip is a laboratory step with a
  restore; the AMD ring and the display of the laptop are still ahead.
* **`dash`/`bash`, job control beyond Ctrl+C, `pty`.** That is 2.2.
