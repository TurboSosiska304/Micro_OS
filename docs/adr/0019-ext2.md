# ADR 0019 - ext2, a second reader and the first with inodes

* Status: accepted, implemented; the write side of 1.4 is ADR 0029
* Date: 2026-11-21

## Context

FAT gave the kernel a volume of the world, but a FAT record has no mode, no
owner and no time of its own: `stat` answers zero for the first two, and
nothing reports the third. The VFS gained a mode (ADR 0005) and the moments
of a change (ADR 0013) for MicroFS, and the only filesystems that could fill
them were the one the kernel formats. The platform roadmap (K6) asked for
the next reader, and the natural next one is the format of a Linux disk:
a superblock, a table of group descriptors, an inode for every object and
blocks that a file reaches through direct and indirect pointers.

FAT also stops at 8.3 or at a long name that a run of UTF-16 entries builds.
ext2 keeps the name in the entry itself, up to 255 bytes, and a directory
that is a stream of variable-length records. It is the first volume of the
world that a person can check with a tool of that world (`e2fsck`), which
makes it the first one whose damage the kernel can describe against a
specification rather than against its own format.

## Decision

### 1. What is read

The component (`components/fs_ext2/`) speaks the ext2 format of a volume of
1024, 2048 or 4096 bytes per block:

* the **superblock** at byte 1024, with the magic `0xEF53`, the block size
  (`s_log_block_size` 0, 1 or 2), the count of blocks and inodes, the size
  of an inode and the geometry of a group;
* the **group descriptors** of 32 bytes, read on demand from the block
  after the superblock; the inode table of a group is the block the
  descriptor names;
* the **inode table**, one inode of 128 bytes or more for every object,
  numbered from 1 and reached by the group and the index inside it; the
  root directory is inode 2;
* the **direct blocks** 0..11 of an inode, the **single**, the **double**
  and the **triple indirection** (blocks 12, 13 and 14); a pointer of zero
  is a hole and reads as zeros, a block number outside the volume is
  `KERR_IO`;
* the **directories**: records of `inode`, `rec_len`, `name_len`, the file
  type when the volume has the `FILETYPE` feature, and the name; the walk
  of a name is byte for byte and case sensitive; `.` and `..` are entries
  like any other on the medium and are hidden from a listing.

A name of a directory entry is at most 255 bytes. `struct vfs_dirent` has a
window of `VFS_NAME_MAX` (32) bytes, so a listing cuts a longer name at a
UTF-8 character boundary, exactly as FAT does; a path that names the file
whole still reaches it, because the lookup compares the name of the medium.
The path itself is bounded by `VFS_PATH_MAX` (128), so a name above that
window is reachable through a shorter mount point but not through any mount
point at all if it does not fit the path.

A volume of the format with a **journal** (ext3) is refused with
`KERR_NOTSUP`: a journal is replayed by a writer, and this component never
writes. The same answer is for the incompatible features that change the
shape of the metadata - `extents`, `64BIT`, `META_BG`, `FLEX_BG` - and for
`HUGE_FILE`; the compatible and read-only-compatible bits that do not change
the layout are accepted, because a read-only mount may ignore what it does
not have to honour. A volume without `FILETYPE` is read as well: the name
length is then the 16-bit field of the older layout, and the type of an
entry comes from its inode.

### 2. The attributes of an inode

`mode` is `i_mode & 0777`, the nine bits the VFS checks and `ls -l` prints;
`owner` is `i_uid` as the medium holds it. The system has one user
(ADR 0005), so a uid is a number that is reported and never a second party:
the VFS reads the triad of that uid and grants nothing beyond it, and an
object of another owner is answered by the triad of the others. `chmod` and
`chown` are absent from the operations, so the VFS answers them with
`KERR_NOTSUP`: the value is on the medium and this reader cannot change it.

`statx` reports `i_mtime` and `i_ctime` as the seconds of Unix they are. The
format has no field that an access updates, which is the field the VFS
deliberately does not have either. A regular file keeps the high half of its
size in the field the old layout called the directory ACL, so a file of a
64-bit size is read correctly up to the limit of the VFS offset.

A symbolic link, a device node, a fifo or a socket is reported with the
type 3 of a non-file and is `KERR_NOTSUP` at `open`: the VFS has no
"follow the link" contract, and inventing one here would make the first
filesystem with links a change of the interface rather than of the reader.

### 3. The reader never writes

The operations `write`, `mkdir`, `unlink`, `chmod` and `chown` are left
empty in the table of the filesystem. The VFS already answers an empty
operation with `KERR_NOTSUP` (the same word MicroFS uses for a call it does
not have), so the adapter has no second path that could write by accident.
An `open` that asks for `O_WRONLY`, `O_RDWR`, `O_CREAT`, `O_TRUNC` or
`O_APPEND` is refused with `KERR_NOTSUP` before the medium is read: the
volume cannot keep the promise of the descriptor, and a descriptor whose
first `write` fails is a worse answer than a refusal at the door.

There is no write path, no journal replay and no repair. The image of the
tests is summed before and after a test that tries every write, and the sum
does not move; the device has a `sync` of its own, and the reader never asks
it. A volume that a power cut caught on another machine is described as it
is; `e2fsck` is the tool of the format, and the kernel does not grow a
second one in this iteration.

### 4. One volume, one lock, one sector cache

Like MicroFS and FAT, the reader keeps one volume in a static slot: a second
ext2 volume is a second mount of the same component in a later version, not
a second design. Every public call takes the recursive `k_mutex` of the
volume, because the walk of a path reads a directory and then the inode it
names. The device cache holds one sector of 512 or 1024 bytes; a block of
1024, 2048 or 4096 bytes is read through it. There is no cache of blocks or
inodes: the format is small enough that a reader of a card can afford the
reads, and a cache that is not invalidated is how a mounted volume and its
medium disagree.

The mount validates the superblock and the first group descriptor before it
answers 0: the block size, the first data block, the count of groups, the
size of an inode, the table of the first group and the size of the volume
against the size of the device. A volume that is larger than its device is
refused; a block number or an inode number that leaves the volume is
`KERR_IO` when a path reaches it. The other groups are validated by the
same arithmetic when an inode of them is read.

### 5. The feature flag and the image

| Option | Host build | ESP32 (Kconfig) | x86-64 (CMake) | Null port |
|---|---|---|---|---|
| `MICRO_OS_FS_EXT2` | ON | `n` by default | OFF by default | not linked |

The host build links the component and the tests run against it, because
the tests are the place where the format is exercised. `make test-minimal`
turns the option off and compiles the three source files into the test
binary directly, exactly as it does for FAT: the flag says what an *image*
links, not what the tests can reach. The x86-64 project has the same option
and registers the type at the boot when it is on (`ports/port_x86_64`).
The board builds the component when `CONFIG_MICRO_OS_FS_EXT2=y`, but the
boot of `main/` does not register the type yet: a board image with the
option on links a reader that the shell cannot name until its boot calls
`ext2_vfs_register_type()`. That is recorded in `docs/debts.md` rather than
hidden in this decision.

### 6. The tests

`tests/cases/test_fs_ext2.c` builds the image itself, byte by byte: 256
blocks of 1024 bytes, one group, a table of 32 inodes, a root directory, a
subdirectory, a file with a mode, an owner and two moments, a name of 104
bytes, an inode outside the table and one file that uses the direct blocks
and all three levels of indirection around a hole. The tests mount the
volume next to MicroFS, list it, read it, ask for `statx`, try every write
and every create, and then damage the same image: a magic that is not one,
a block size the format does not have, an extent tree, a journal, an inode
table that is not there, a double-indirection table that names a block
outside the volume and a directory entry whose name does not fit its
record. The shell is exercised through `mount ... ext2`, `ls`, `cat`,
`stat` and `umount`.

`mke2fs` is not a dependency of the tests. An image that the test writes is
an image whose bytes the test knows, and a reader that finds a name, a size
or a moment is answering about those bytes and not about the tool of the
machine that runs the suite.

## Consequences

**Good**

* The VFS has a second reader with real modes, owners and times, and the
  first filesystem of the world whose format a checker of the world can
  walk.
* The shape of the reader - superblock, group, inode, indirect block - is
  the shape the kernel needs for a writable ext2 and for an inode-based
  format of its own later.
* A damaged ext2 volume has answers that name the damage (`KERR_INVAL` for
  a superblock or a geometry, `KERR_NOTSUP` for a feature, `KERR_IO` for a
  block or an inode outside the volume) instead of reading it as zeros.

**Bad**

* This reader is read-only and one volume at a time; a write, a new name, a
  mode and an owner are `KERR_NOTSUP`, and there is no `fsck ext2`. The
  write side of the format is ADR 0029 (M2.2 of the plan of 1.4), and it
  leaves these reader rules alone.
* A journal is not replayed: an ext3 volume that was not unmounted cleanly
  is refused, and a volume of ext4 is refused for its extents.
* The names of a listing are cut at the window of `struct vfs_dirent`,
  which is shorter than the 255 bytes of the format; a person who wants to
  see the whole name needs a path that names the file, or a wider window
  of the VFS later.
* The board image links the reader but does not register its type yet.
