# ADR 0002 — Слой исполнения: своё ядро поверх FreeRTOS

> English version: [0002-scheduler-substrate.md](0002-scheduler-substrate.md)

* Статус: принято (фаза 1 в работе)
* Дата: 2026-10-21

## Контекст

Чтобы процесс в Linux мог быть вытеснен в произвольный момент, планировщик должен
уметь переключить контекст. На ESP32 есть два пути:

1. **FreeRTOS как субстрат.** Каждая задача ядра — это задача FreeRTOS, приоритеты
   мапятся один в один, переключение контекста делает FreeRTOS. Наш планировщик
   становится «мета-планировщиком» поверх: он решает, *какая* из задач FreeRTOS
   должна быть активна, а переключение уже происходит силами FreeRTOS.
2. **Собственный планировщик поверх FreeRTOS.** Используется одна служебная задача
   FreeRTOS (или ISR-триггер), а переключение контекста между нашими задачами
   выполняем сами: сохраняем/восстанавливаем указатели стека и регистры.

## Решение

Начинаем с **варианта 1**: задача ядра = задача FreeRTOS, один-к-одному
соответствие. Это даёт вытеснение «из коробки», проверенную реализацию
сохранения контекста на Xtensa и возможность не трогать WiFi-стек.

Вариант 2 (собственный планировщик) переносится на позднюю стазию, когда
понадобится то, чего FreeRTOS не даёт:

* несколько задач ядра, разделённых по уровням приоритета *внутри* одного
  кванта FreeRTOS (Linux-подобная справедливость между процессами);
* «системные вызовы» с переключением контекста в произвольной точке;
* точный учёт квантов и времени ЦП.

Переключение реализуется через `esp_cpu_set_pc`/`portYIELD` с ручным
сохранением регистров Xtensa (как это делает FreeRTOS для xPort).

## Последствия

**Хорошие:**

* Работающая многозадачность уже в фазе 1 без рискованных низкоуровневых трюков.
* WiFi/BLE/TLS продолжают работать: они живут в задачах FreeRTOS.
* Ошибки в планировщике не приводят к «зависанию в IRAM» — FreeRTOS восстановит
  задачу из watchdog.

**Плохие:**

* Точное поведение приоритетов не совпадает с Linux: планировщик FreeRTOS
  переключает задачи по своим правилам (time slicing), наш уровень приоритета —
  поверх.
* Два уровня приоритетов (FreeRTOS + наш) могут конфликтовать: нужно аккуратно
  выбирать приоритет задачи FreeRTOS для наших задач.

## Побочные находки фазы 1F

Доктор железа нашёл три ошибки, которые невозможно поймать без живого устройства:

1. **I2C-драйвер IDF 5.3**: последний аргумент `i2c_master_transmit()` — это
   таймаут в миллисекундах, а не флаг. Значение `true` означало 1 мс, и
   транзакции обрывались в зависимости от фазы загрузки. С таймаутом 100 мс
   шига работает стабильно.
2. **SPI через GPIO-матрицу** ограничен 26.7 МГц, 40 МГц — отказ
   `assigned clock speed not supported`. Дисплей работает на 20 МГц.
3. **DMA SPI на ESP32 не читает PSRAM**: кадровый буфер отправляется на экран
   порциями по 4 КБ через внутренний буфер.

Вывод: hardware doctor — не формальность, а рабочий инструмент. Каждая из
этих ошибок выглядела как «устройство сломан��», хотя код был неправильным.
