# CI Micro OS

> English version: [ci.md](ci.md)

Автосборка релиз-кандидата. Каждый пуш в `release_candidate` собирает прошивку
для ESP32 и проверяет целостность репозитория и пакета для прошивки. Тег вида
`vX.Y.Z` публикует пакет как релиз GitHub.

Тесты самого кода в этот workflow не входят: они принадлежат контрибьютору,
на его машине, пока после первого релиза они не получат собственный CI/CD.
CI говорит про то, что уходит на плату.

Всё это один workflow: [.github/workflows/ci.yml](../.github/workflows/ci.yml).

## Триггеры

| Событие | Ветки | Что происходит |
|---------|-------|----------------|
| push | `release_candidate`, `mainline` | сборка и проверки |
| push | теги `v*` | то же самое, и потом релиз |
| pull request | в `release_candidate`, `mainline` | сборка и проверки |
| schedule | по понедельникам, 04:23 UTC | то же: зависимости стареют, сборка всё равно должна работать |
| вручную | — | то же, из вкладки Actions |

Запуск по расписанию берётся из ветки по умолчанию, поэтому он заработает
только когда workflow дойдёт до ветки по умолчанию.

## Задачи (jobs)

| Job | Что делает | Примечания |
|-----|------------|------------|
| `integrity` | проверка целостности репозитория и пакета | забирается вся история, `git fsck` должен пройти |
| `firmware` | прошивка для ESP32, сборка пакета, проверка свежих бинарников | официальный образ `espressif/idf:v5.3` |
| `release` | публикует пакет как релиз GitHub | только для тегов и только после того, как все остальные задачи зелёные |

Сборка и проверка блокирующие: ветка не зелёная, пока не собрана прошивка и
не прошла проверка целостности.

### Тестов здесь нет

Юнит-тесты и smoke-тест симулятора — это тесты самого кода, их гоняет
контрибьютор на своей машине перед пушем (см.
[«Как запустить это локально»](#как-запустить-это-локально)). Юнит-тесты —
это тесты из `tests/`. Smoke-тест проверяет ядро целиком: симулятор
загружается, подсистемы поднимаются, шелл отвечает на команды. Это самый
дешёвый сквозной тест ядра, он ловит то, чего не видно в юнит-тестах,
например задачу, которая никогда не просыпается.

Они намеренно не входят в автосборку, а после первого релиза получают
собственный CI/CD — отдельный workflow, не связанный с этим.

### Прошивка

Сборка идёт внутри официального образа ESP-IDF, поэтому инструментарий ровно
тот же, что и на машине разработчика. Команды IDF попадают в `PATH` только
после `export.sh` — образ держит IDF в `/opt/esp/idf` и говорит об этом в
`IDF_PATH` — поэтому каждый шаг сборки сначала подключает его:

```bash
. "$IDF_PATH/export.sh"
idf.py --version
idf.py set-target esp32
idf.py build
idf.py size
tools/bundle.sh build dist
```

Версия ESP-IDF зафиксирована тегом образа (`espressif/idf:v5.3`): это ветка
`release-v5.3` ESP-IDF, ровно та версия, под которую написан проект.

После сборки пакет собирается и проверяется: свежие бинарники сверяются с
`partitions.csv` и `sdkconfig.defaults`, магия образа — с форматом ESP-IDF,
суммы пересчитываются заново.

## Проверка целостности

`tools/integrity_check.py` — сердце проверки. Зависимостей нет, только
стандартная библиотека Python, поэтому один и тот же скрипт работает и на
ноутбуке, и на машине CI.

```bash
make integrity          # вся проверка
tools/integrity_check.py --verbose --json report.json
```

| Группа | Что проверяется |
|--------|-----------------|
| `bundle` | файлы `dist/` на месте, SHA-256 совпадают, скрипт прошивки исполняемый и прошивает все бинарники |
| `image` | заголовок образа ESP: магия `0xE9`, чип ESP32, выравнивание по 16 байт, число сегментов |
| `partition` | собранная таблица разделов против `partitions.csv`: имена, типы, смещения и размеры, плюс MD5, который ESP-IDF пишет в таблицу |
| `config` | размер флеша из `sdkconfig.defaults` против заголовка образов и против разделов: ничего не выходит за флеш |
| `git` | `git fsck --strict`: объекты репозитория целы |
| `sources` | гигиена исходников: UTF-8, LF, финальный перевод строки, нет висячих пробелов, нет табов, строки C не длиннее 100 символов |
| `format` | C-исходники отформатированы (`clang-format --dry-run --Werror`) |
| `version` | версия ядра совпадает с тегом (только для релизов) |

Проверка строгая намеренно: это защита от пакета, который не соответствует
исходникам, из которых он собран.

`dist/` — продукт сборки, а не файл репозитория. На свежем чекауте группы
`bundle`, `image` и `partition` пропускаются — проверять нечего — а группа
`config` говорит только про `sdkconfig.defaults`, который лежит в исходниках.
Задача `firmware` в CI собирает пакет и проверяет свежие бинарники тем же
скриптом, с `--skip-git --skip-format`: объекты git и форматирование
исходников — дело задачи `integrity`.

## Артефакты и релиз

Каждый запуск выкладывает:

| Артефакт | Что внутри |
|----------|------------|
| `integrity-report` | отчёт о проверке целостности в JSON |
| `firmware` | `dist/` с бинарниками, суммами и скриптом прошивки, плюс `micro_os.elf` и `micro_os.map` для отладки |

Тег вида `vX.Y.Z` публикует релиз GitHub с пакетом:

```bash
git tag v0.1.0
git push origin v0.1.0
```

Задача релиза проверяет, что версия ядра в
`components/kernel/include/kernel/config.h` совпадает с версией тега, и что
суммы скачанного пакета совпадают с бинарниками. Архивы Actions не хранят
права файлов, поэтому скрипту прошивки возвращают бит исполнения перед
публикацией.

Символы (`micro_os.elf`, `micro_os.map`) лежат в релизе для отладки: для
прошивки платы они не нужны.

## Как запустить это локально

CI пока тесты не гоняет: это работа контрибьютора, на его машине. Всё
сразу:

```bash
make ci          # сборка, тесты, smoke-тест и проверка целостности
```

Прошивка собирается руками, потому что ESP-IDF стоит не везде:

```bash
make idf-build   # прошивка
make bundle      # прошивка в dist/ вместе с суммами и скриптом прошивки
make integrity   # проверка свежего пакета
```

## Зафиксированные версии

| Что | Версия | Зачем |
|-----|--------|-------|
| ESP-IDF | `v5.3` | та же, под которую написан проект и которой собирается прошивка |
| clang-format | `23.1.3` | другая версия форматирует исходники по-своему, и проверка падала бы без причины |

Компилятор хоста — GCC, тот же, что использует ESP-IDF.
